## 2. Why selection was the next unit event

Priority was judged by registrations **and** implementability, not by count alone:

| Candidate | Registrations | Why not / why now |
|---|---:|---|
| attacked (18) | 512 | Needs a real attack swing, damage calculation, targets and combat timers. Publishing without those transitions would fabricate gameplay. |
| death (20) | 480 | Needs real damage application and lifecycle rules before a death event is truthful. |
| spell effect (274) | 480 | Needs abilities, cast validation, mana/cooldown and spell targets; out of scope before orders/combat. |
| **selected (24)** | **16** | One reachable trigger with a real action; producer is a genuine selection state transition; foundation for orders; verifiable against the map's own hashtable state. |

The selected trigger `gg_trg____________________005` is registered for all 16 players and its action is
reachable: `SaveUnitHandle(YDHT, GetHandleId(GetTriggerPlayer()), 0x2C1C8DD5, GetTriggerUnit())`.
The map also calls `SelectUnitForPlayerSingle` (`ClearSelection` + `SelectUnit`) in its own code, so the
selection command path is a real map dependency, not a test invention.

Selection was implemented first. Orders, movement and combat remain unimplemented and are the next
dependency chain.

## 3. Architecture

### Event bus

- `JassEventRegistration`: kind, exact event ID, player, source handle (unit/dialog/button/timer/region),
  filter, trigger, registration function, site/chain, counters.
- `JassEvent`: typed payload; only fields valid for the producing event are populated.
- Scoped `JassEventContext` stack: every dispatch pushes/pops; `TriggerExecute` swaps only
  `Context.Trigger` and restores it. Nested triggers and nested event dispatches restore the outer context.
- Conditions run after optional filters and before actions. Disabled triggers are skipped; destroyed
  triggers remove their registrations; callback failures restore context, count failures and rethrow.
- Producers: timer, timer-expire, chat, dialog, dialog-button, selection/deselection.

### Selection producer

`JassGameRuntime` keeps one selection set per player and exposes:
`SelectUnit(unit, player, add)`, `DeselectUnit`, `ClearSelection`, `SelectSingleUnit` (UI click semantics)
and `RemoveUnit` cleanup. Rules:

- Owner-only: a player can select only a unit whose `OwnerId` matches that player.
- Selecting an already selected unit produces no event (no per-frame duplicate dispatch).
- `SelectUnit(flag=false)`, `ClearSelection`, `DeselectUnit` publish `EVENT_PLAYER_UNIT_DESELECTED` (25)
  and the unit-scoped `EVENT_UNIT_DESELECTED` (58) only for registrations matching that unit.
- Adding a unit publishes `EVENT_PLAYER_UNIT_SELECTED` (24) for the selecting player and
  `EVENT_UNIT_SELECTED` (57) only for unit-scoped registrations whose source handle is that unit.
- Payload: `GetTriggerUnit` = selected unit, `GetTriggerPlayer` = selecting player,
  `GetTriggeringTrigger` = executing trigger. Unrelated response values remain null/empty.
- Removing a unit clears it from every selection set without leaving stale handles.
- JASS natives `SelectUnit(unit, flag)` and `ClearSelection()` use the same producer for the local player
  (player 0); `SelectUnitForPlayerSingle` in Blizzard.j therefore works through the real path.

The viewer projects runtime units into screen space, picks the nearest unit within 45 px of a real left click,
and calls `ViewerInput.SelectUnit` (engine input adapter). `--select-unit <index>` drives the same adapter for
deterministic screenshots. Only units owned by the local player are click-selectable; the target map starts with
no player-0 units, so the screenshot demonstration selects owner player 8's unit through the same API.

Visible output: green selection brackets at the unit's projected position and a
`selected P<player> <rawcode> hp ...` line in the map overlay.

Selection details:

- The map trigger `gg_trg____________________005` ran once; `GetTriggerUnit`/`GetTriggerPlayer` returned the

  selection survives timer advancement and `ClearSelection` empties it.

## 5. Tests

1. Dialog click dispatch + nested `TriggerExecute` context restoration.
2. Nested event dispatch (dialog action -> chat event) restores the outer clicked-button context.
3. Dialog filters, disabled triggers, destroyed-trigger cleanup, exact dialog-button matching, timer context.
4. Engine input adapter for dialog and selection.
5. Registration order and condition-before-action ordering.
6. Throwing callback restores context and leaves the bus usable.
7. Selection: owner-only, player-unit + unit-scoped dispatch, `GetTriggerUnit`/`GetTriggerPlayer` values.

10. Selection filter blocks the callback.

selected state, wrong-player rejection and cleanup. Total: **67 tests** (53 original + 14 event tests).

## 8. Remaining gaps (explicit, not stubbed)

- Orders (`EVENT_PLAYER_UNIT_ISSUED_*`), attack/damage/death (`18/20/52`), spells (`274/275`), items (`48/49/50/277`),
  player leave, regions, game state, YDWE key/mouse/sync have no producer; their registrations stay level 1.
- Response natives still missing for those families: `GetManipulatedItem`, `GetTrainedUnit`, `GetBuyingUnit`,
  `GetSoldUnit`, `GetSoldItem`, `GetLevelingUnit`, `GetHeroLevel`, `GetUpgradingUnit`, `GetResearched`,
  `GetTriggeringRegion`, `GetEnteringUnit/LeavingUnit`, and game-state responses. They are listed per family
  in the JSON and return nothing only because they are not registered (no fabricated defaults).
- Orders/movement are the next dependency after selection; combat needs attack swings and real damage first.
- `timer-expire` producer exists but its subscriptions did not fire in the 4 s audit (level 2).
- TriggerSleepAction/coroutines remain unsupported (target map does not use them on this path).
- Lua 5.4 vs target 5.3.6 is not bit-identical; 12 numeric/string semantics are covered by tests.
- UI font covers ASCII/Latin/Vietnamese; CJK map text is shown as `?`.
- 196 map-declared extension natives remain unimplemented.
